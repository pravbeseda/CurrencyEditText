# Security — audit 2026-10-22

## SEC-1 · blocking · Reading the field goes through `Double`: a 310-digit paste crashes the host app, and amounts above ~16 significant digits come back rounded

- **Where:** `library/src/main/java/ru/pravbeseda/currencyedittext/util/Utils.kt:38-54` (`NumberFormat…parse` at :47), `library/src/main/java/ru/pravbeseda/currencyedittext/CurrencyEditText.kt:315-323` (`stringToBigDecimal`); reached from `CurrencyEditText.kt:293` (watcher `onValueChanged`, on every keystroke), `:115` (`getValue`), `:118`, `:126`, `:150`, `:178` (setLocale / applySeparators / setEmptyStringForZero read the value and write it back), `:237` (calculator seed)
- **What this is:** Every read of the field's number strips the separators, parses the string with `NumberFormat.parse`, and builds a `BigDecimal` from that `Number`'s `toString()`.
- **Problem:** `NumberFormat.parse` returns a `Long` or a `Double`, never a `BigDecimal`. For `"1"` followed by 309 zeros it returns `Double.POSITIVE_INFINITY`, and `BigDecimal("Infinity")` throws `NumberFormatException`. The field has no length cap and `DigitsKeyListener` admits digits, so typing or pasting a 310-digit number throws inside `afterTextChanged` on the main thread (`CurrencyInputWatcher.kt:54` always calls `onValueChanged`; `EasyTextWatcher.afterTextChanged` catches nothing) and the consumer's app crashes. Below that size the value is silently wrong: `"12345678901234567.89"` reads as `12345678901234568`, `99 999 999 999 999.99` as `99999999999999.98`. The host gets the rounded value from `getValue()` and `onValueChanged`, and `setLocale`, `setSeparators` and `setEmptyStringForZero` write it back into the field, overwriting what the user typed. The calculator already parses the same digit string exactly with `String.toBigDecimalOrNull()` (`calculator/ExpressionEvaluator.kt:142`).
- **Fix direction:** Parse the cleaned string straight into a `BigDecimal` (`toBigDecimalOrNull() ?: BigDecimal.ZERO`), which deletes the `NumberFormat`, the `Number` round-trip and the try/catch. An exact parse keeps scale (`"0.00"` → `0.00`, `"1.50"` → `1.50` instead of today's `1.5`), so the zero check in `setValue` must move to `signum() == 0` in the same change (COR-3), and the scale change is a consumer-visible behaviour change to call out in the PR. Start with regression tests of a 310-digit, a 20-digit and a `"0.00"` string in `UtilsTest`.
- **If we skip it:** Any end user can crash any app that uses the field with one paste, and large amounts reach the host rounded.
- **Effort:** S · **Touches:** `util/Utils.kt`, `CurrencyEditText.kt`, `src/test/.../util/UtilsTest.kt` · **Depends on:** COR-3 (same change) · **Status:** new · **Verified:** confirmed (JVM; not run on ART)

## SEC-2 · blocking · `setValue` drops every fractional digit past the second, whatever `maxNumberOfDecimalPlaces` is

- **Where:** `library/src/main/java/ru/pravbeseda/currencyedittext/util/Utils.kt:56-66` (pattern `"#,##0.##"` at :64), `library/src/main/java/ru/pravbeseda/currencyedittext/CurrencyEditText.kt:100-112`; callers `CurrencyEditText.kt:117-131` (`setLocale` ×2), `:145-156` (`applySeparators`), `:176-179` (`setEmptyStringForZero`), `:235-239` (calculator `scale = maxDecimalPlaces`, `onAccept = ::setValue`), `CurrencyMaterialEditText.kt:86,91`; contradicted by `README.md:271-272`
- **What this is:** `formatMoneyValue` turns a `BigDecimal` into the text `setValue` writes into the field; every programmatic write goes through it — re-rendering after a locale or separator change, toggling `emptyStringForZero`, and the calculator's `=`.
- **Problem:** The pattern allows at most 2 fraction digits and rounds HALF_EVEN; it never sees the field's `maxNumberOfDecimalPlaces`, which the formatter pipeline and the calculator both respect. With `maxNumberOfDecimalPlaces = 3`: `setValue(BigDecimal("0.125"))` shows `0.12`, `setValue(BigDecimal("1.005"))` shows `1`; typing `1.235` and calling `setLocale(...)` or `setSeparators(...)` rewrites it as `1.24`; the calculator evaluates `1/8` to `0.125` and the field shows `0.12`, although the README says the result is "rounded to `maxNumberOfDecimalPlaces`". No test pins the 2-place behaviour.
- **Fix direction:** One formatter in `util/` that takes the field's decimal places and writes them into the pattern as optional `#` digits (not `0`, which would pad), shared with `Routines.bigDecimalToString` (ARCH-5). The red test belongs in `src/test` (`UtilsTest` has no `formatMoneyValue` test today).
- **If we skip it:** Any consumer using more than 2 decimal places (unit prices, exchange rates, crypto) silently loses digits whenever the library re-renders the value.
- **Effort:** S · **Touches:** `util/Utils.kt`, `CurrencyEditText.kt`, `util/UtilsTest.kt` · **Depends on:** — · **Status:** new · **Verified:** confirmed
